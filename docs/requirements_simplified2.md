## 0. Важное открытие — меняем модель данных

До этого момента `Match` в бэкенде проектировался как **дуэль между двумя пользователями приложения** (player1/player2 ищут друг друга, играют, у одного из них win/loss). Судя по новым скриншотам Figma ("Play" со списком матчей: "Malta Vibes / Counter-Strike / Entropiq vs Trasko / 2h 5min") и тексту задания — это **не дуэли между игроками**, а **ставки на реальные киберспортивные матчи**, данные о которых приходят из внешнего фида (PandaScore). Пользователь не играет сам — он делает ставку (gg-монетами) на то, какая из двух команд победит в реальном матче.

Из этого следует: старую модель `Match` (player1/player2/score1/score2) нужно переопределить под реальный киберспортивный матч, и добавить новую модель `Bet` — ставку пользователя на исход матча. `Profile.gg_balance` и `Leaderboard` логику менять не нужно, они уже корректны.

## 2. Работа с PandaScore

- **Документация:** https://developers.pandascore.co/docs/introduction
- **Аутентификация:** заголовок `Authorization: Bearer <token>` (токен — в `.env`, не в коде и не в git).
- **Эндпоинты:**
  - `GET https://api.pandascore.co/matches/upcoming` — предстоящие матчи.
  - `GET https://api.pandascore.co/matches/running` — идущие сейчас.
  - `GET https://api.pandascore.co/matches/past` — завершённые (для определения победителя и расчёта ставок).
  - Пагинация: `page`, `per_page` (до 100).
- **Лимит бесплатного тарифа:** 1000 запросов/час — при опросе раз в минуту (60 запросов/час на каждый из трёх эндпоинтов = 180/час) укладываемся с большим запасом.
- **Cron:** системный cron / Celery beat / `django-crontab` — раз в минуту дергать все три эндпоинта, апсертить `Match` по `pandascore_id`, для новых `past`-матчей запускать резолв ставок.

## 3. Модели данных (Django)

```python
class Match(models.Model):
    pandascore_id = models.BigIntegerField(unique=True)
    tournament_name = models.CharField(max_length=255)
    videogame = models.CharField(max_length=100)  # "Counter-Strike", "League of Legends", ...
    team1_name = models.CharField(max_length=100)
    team1_logo_url = models.URLField(blank=True)
    team2_name = models.CharField(max_length=100)
    team2_logo_url = models.URLField(blank=True)
    scheduled_at = models.DateTimeField()
    status = models.CharField(
        max_length=20,
        choices=[("upcoming", "Upcoming"), ("running", "Running"), ("finished", "Finished"), ("cancelled", "Cancelled")],
    )
    winner_name = models.CharField(max_length=100, blank=True, null=True)  # заполняется по завершении
    bets_resolved = models.BooleanField(default=False)  # чтобы cron не пересчитал ставки дважды

class Bet(models.Model):
    user = models.ForeignKey(User, on_delete=models.CASCADE, related_name="bets")
    match = models.ForeignKey(Match, on_delete=models.CASCADE, related_name="bets")
    chosen_team = models.CharField(max_length=100)  # значение team1_name или team2_name на момент ставки
    stake = models.PositiveIntegerField()
    status = models.CharField(
        max_length=20,
        choices=[("active", "Active"), ("won", "Won"), ("lost", "Lost")],
        default="active",
    )
    payout = models.PositiveIntegerField(default=0)  # 0, пока не разрешилось; stake*2 при выигрыше
    created_at = models.DateTimeField(auto_now_add=True)
    resolved_at = models.DateTimeField(null=True, blank=True)

    class Meta:
        # опционально: одна активная ставка на матч на пользователя
        constraints = [
            models.UniqueConstraint(
                fields=["user", "match"],
                condition=models.Q(status="active"),
                name="one_active_bet_per_match",
            )
        ]
```

**Правила:**
- Ставку можно сделать только на матч со `status="upcoming"` (нельзя ставить на уже идущий/завершённый — если бизнес хочет разрешить live-ставки на `running`, это отдельное решение, по умолчанию делаем только на `upcoming`).
- При создании `Bet`: списать `stake` из `Profile.gg_balance` **сразу** (транзакция — списание баланса и создание ставки атомарно, чтобы не было гонки при двойном сабмите).
- При переводе `Match.status` в `finished` (из cron-джобы): определить `winner_name` по данным PandaScore, затем для каждой связанной активной `Bet`:
  - если `chosen_team == winner_name` → `status="won"`, `payout = stake * 2`, начислить `payout` на `gg_balance`.
  - иначе → `status="lost"`, `payout=0` (баланс не трогаем, стейк уже был списан при ставке).
  - выставить `bets_resolved=True` на матче, чтобы cron не повторял расчёт.

## 4. API-контракт (дополнение к `docs/screens_and_api.md`)

- `GET /api/matches/?status=upcoming|running` → список матчей + `user_bet` (вложенный объект текущей ставки пользователя на этот матч, либо `null`).
- `POST /api/bets/` — body `{match_id, chosen_team, stake}` → создаёт ставку или `400` с ошибкой (недостаточно баланса / матч уже начался / уже есть активная ставка на этот матч).
- `GET /api/bets/history/` → список ставок пользователя (won/lost/active), с данными матча (команды, дата, турнир) и `payout`/`stake`.
- `POST /api/account/get-coins/` → мок начисления монет за "просмотр рекламы" (фиксированная сумма, например `+50 gg`).
- `PATCH /api/account/me/` (опционально) → обновление `username`/`avatar`.

## 8. Статус реализации — backend (шаги 1-3 из §1)

**Готово и закоммичено в `backend/`:**

- `matches/models.py` — `Match`/`Bet` переопределены в точности по §3.
- `matches/pandascore.py` — тонкий клиент (`fetch_matches("upcoming"|"running"|"past")`), токен читается из `settings.PANDASCORE_API_TOKEN`.
- `matches/management/commands/sync_matches.py` — cron-команда: дергает все три эндпоинта, апсертит `Match` по `pandascore_id` (`update_or_create`), парсит команды/лого из `opponents`, определяет `winner_name` по `winner`/`winner_id` из ответа PandaScore, и при переходе матча в `finished` атомарно (`select_for_update` на `Match`+`Bet`+`Profile`) начисляет `stake*2` победителям и помечает проигравших, выставляя `bets_resolved=True`.
- `matches/serializers.py`, `matches/views.py`, `matches/urls.py` — реализован API из §4: `GET /api/matches/` (с `?status=` фильтром и `user_bet` в каждой карточке), `POST /api/bets/`, `GET /api/bets/history/`.
- `matches/admin.py` — CRUD для `Match`/`Bet` в админке (куратор может руками поправить статус/победителя).
- `config/settings.py` — добавлена `PANDASCORE_API_TOKEN = env("PANDASCORE_API_TOKEN", default="")`.
- `requirements.txt` — добавлен `requests`.

**Уточнение к API-контракту (правка §4):** тело `POST /api/bets/` использует ключ **`match_id`** — уточняем явно здесь, чтобы не разъезжалось с мобильной реализацией: `{"match_id": <id>, "chosen_team": "<team name>", "stake": <int>}`. Ответ на успех — `201` с `{id, match_id, chosen_team, stake, status, payout, created_at}`. Ответ на ошибку — `400` с полем-ключом ошибки (`{"stake": "Insufficient gg balance."}` и т.п.) — этот формат мобильная часть должна парсить для текста в модалке ошибки.

**Принятые решения по открытым вопросам §6 (default, пока не сказано иное):**
1. Ставки принимаются только на матчи со `status="upcoming"` (п.1 из открытых вопросов) — на `running`/`finished` `POST /api/bets/` вернёт `400`.
2. Ограничения на мин/макс ставку **не** реализованы (п.2) — только `stake > 0` и `stake <= gg_balance`.
3. Отмена ставки пользователем (п.4) — **не реализована**; ставка живёт до резолва матча.
4. Список игр/турниров не фильтруется (п.5) — синхронизируются все матчи, которые отдаёт PandaScore по трём эндпоинтам.

**Важно — требует действий на сервере/локально, ещё не сделано:**

1. **Потеря данных в таблице `matches_match`**: старая схема (`player1`/`player2`/`score1`/`score2`) несовместима с новой (`pandascore_id`/`team1_name`/...). Django не сможет смигрировать данные автоматически. Раз это тестовые/учебные данные — самый простой путь: удалить старые миграции матчей и накатить заново, либо (safer) сделать `makemigrations` как обычно и, если Django попросит default для новых обязательных полей на непустой таблице, ответить "1) provide a one-off default" и **очистить таблицу `Match`/`Bet` вручную после миграции** (`python manage.py shell` → `Match.objects.all().delete()`), т.к. любые старые "дуэльные" записи всё равно бессмысленны в новой модели.
2. **Мобильное приложение временно сломается на экранах Play/History**: старые эндпоинты `matches/current/`, `matches/search/`, `matches/history/` больше не существуют (на их месте — заглушки/новые `matches/`, `bets/`, `bets/history/`). Экраны `PlayScreen`/`HistoryScreen` нужно переписать под новый контракт (шаги 4 и 6 из §1) — до этого момента приложение будет получать 404 на этих экранах. Это ожидаемо и будет закрыто следующим шагом.

**Дальше по плану:** локально поставить `requests` (`pip install -r requirements.txt`), `python manage.py makemigrations matches && python manage.py migrate`, проверить `python manage.py sync_matches` вручную (должен подтянуть реальные матчи с PandaScore), задеплоить на сервер, добавить `PANDASCORE_API_TOKEN` в серверный `.env` (уже сделано и провалидировано ранее через `curl`), прописать системный cron (`* * * * * cd .../backend && venv/bin/python manage.py sync_matches >> /var/log/expertgg-sync.log 2>&1`), затем переходить к шагам 4-6 (мобильные экраны Play/History/модалки).

**Проверено локально (эта итерация):** старая таблица `matches_match` была пуста и локально, и на проде — миграцию сделали не через "one-off default", а начисто (удалили старый `0001_initial`, сгенерировали новый на чистой модели). `sync_matches` прогнан вручную с реальным PandaScore-токеном — подтянул 106 матчей; полный цикл `GET /api/matches/` → `POST /api/bets/` → `GET /api/bets/history/` проверен через Django test client, списание `gg_balance` подтверждено.

**Найден и исправлен баг в `sync_matches.py`:** в `_upsert_match` фолбэк `scheduled_at = timezone.now()` для матчей без `scheduled_at`/`begin_at` стоял ПОСЛЕ вызова `Match.objects.update_or_create(...)` — но `scheduled_at` обязательное (`NOT NULL`) без дефолта на уровне модели, поэтому сама вставка нового `Match` падала с `IntegrityError` раньше, чем фолбэк успевал сработать (код после `update_or_create` в этом случае просто недостижим). Исправлено: `scheduled_at` теперь всегда попадает в `defaults` до вызова `update_or_create` (с фолбэком на `timezone.now()`, если PandaScore не прислал дату).

## 12. Подтверждённые решения (не требуют вопроса куратору)

- **Одна ставка на матч — подтверждено, оставляем как есть.** Пользователь может поставить только одну ставку на конкретный матч (нельзя добавить ставку на ту же команду ещё раз или поставить сразу на обе команды); ограничение работает и на бэкенде (`UniqueConstraint` на `(user, match)` с условием `status="active"`), и в интерфейсе (карточка с уже сделанной ставкой не раскрывается для новой ставки). При этом ставки на **разные** матчи (в том числе одной и той же игры, например несколько разных CS-матчей) ничем не ограничены.
- **Видимость матча в Play после ставки — уточнено.** Матч остаётся в списке Play, пока его статус `upcoming` или `running` — просто вместо таймера/кнопок показывается "Your bet: `<команда>` • `<ставка>` gg", карточка больше не раскрывается. Как только матч переходит в `finished`, он пропадает из Play и виден только в History (со статусом Win/Lose и итоговым изменением баланса).

## 14. Ответы куратора на открытые вопросы (закрывают §6 и п.1-5 §11)
